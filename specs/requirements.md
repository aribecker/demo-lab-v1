## Weather API
R4. GET /api/weather retrieves fresh data for Buenos Aires, Argentina, latitude -34.6037 and longitude -58.3816. Query Open-Meteo first; on HTTP error, timeout, invalid JSON, missing fields or invalid values, try MET Norway Locationforecast compact. Normalize Celsius, relative humidity percent, wind km/h and timestamps as UTC ISO-8601. Convert MET Norway wind from m/s and choose its forecast hour closest to now. Clearly distinguish current model data from forecast data; never present a forecast as an observation.

R5. Success is HTTP 200 application/json with this contract:
- version: 2.0.0
- city: Buenos Aires, Argentina
- temperatureC: finite number
- feelsLikeC: finite number or null
- humidityPercent: number in [0,100]
- windKmh: nonnegative finite number
- observedAt: valid UTC ISO-8601 instant for the selected data time
- requestedAt: valid UTC ISO-8601 instant for the request
- timezone: America/Argentina/Buenos_Aires
- provider: Open-Meteo or MET Norway
- providerUrl: the provider's attribution website
- dataType: current model data or nearest-hour forecast
- requestId: safe correlation identifier, also returned as X-Request-Id

R6. Limit each provider HTTP request to five seconds, with at most one primary and one fallback attempt per API request. If both fail, return a safe JSON error with code PROVIDER_UNAVAILABLE, message, requestId and retryable=false. Use HTTP 504 if both failures are timeouts, otherwise 502. Never substitute fabricated or cached demonstration data. GET /health returns JSON status UP and version 2.0.0 without querying providers. API and health responses use Cache-Control: no-store. Provider endpoint URLs and timeouts are server configuration, not request parameters.

R7. The API is a public, non-sensitive demonstration. Configure CORS for the exact deployed frontend origin and localhost:5173 through ALLOWED_ORIGINS; allow GET/OPTIONS, expose X-Request-Id and do not use credentials. Record request ID, provider, status/failure and elapsed milliseconds to standard application logs. Do not put credentials in the browser, repository, logs or specifications.

## R15 — Real multi-provider login (v2.2.0)

R16 — Authentication boundary: use Spring Security authorization-code login (Google OIDC; GitHub OAuth2; Microsoft OAuth2 + Graph User.Read). Secrets and provider access/refresh tokens stay on the Java server. Separate OAuth app registrations are required; ChatGPT connectors are unrelated. Enable each provider only when both client ID and secret are configured. Unconfigured providers are visible but disabled with an honest setup status.

R17 — Cross-site handoff: OAuth runs as top-level navigation to the existing API. After validated login redirect only to the configured frontend /login, with a random single-use 60-second ticket in the fragment, bound to a SHA-256 challenge generated by that browser. Exchange requires its original verifier. Remove fragment before network calls. Return an opaque 30-minute demo bearer token and normalized profile; store only the demo token in sessionStorage. No provider token or personal data in URLs. Server stores hashes of bearer/ticket values, bounded in-memory records, and deletes expired/revoked entries. Redeploy invalidates sessions. Reject forged, expired, replayed and wrong-verifier tickets. OAuth state remains Spring-managed.

R18 — Session and failure behavior: restore profile on /login via bearer /auth/me; expire after 30 minutes and allow sign out via bearer POST /auth/logout. No cookie credentials in cross-origin frontend requests. Cancel/denial uses generic error codes, no provider error details. Network errors must not pretend to log out server-side or show a false success; allow retry. Explicitly distinguish local automated validation from real consent with each provider, which requires the owner's app registrations.

## R24 — Virtual BTC/USDT two-balance simulator (v2.4.1)
Upgrade the same `/bitcoin` widget in the parallel environment. Keep the live chart/10-second lifecycle and add a simulation panel beside it on desktop, stacked on phones. Before Start, virtual USDT, BTC, fee and trade counters are zero. Capital defaults to 10,000 USDT and remains configurable. **Start simulation / Reset simulation** clears BTC, all fees, trades and quote history, restores the configured capital as available USDT, and resumes observation without buying. The first fresh quote after Reset only establishes the crossing reference (even if already below the minimum); buy only when a later successful sample crosses from at/above minimum to strictly below it. If unavailable, retain USDT and wait without executing. No real exchange account, credentials, orders or transactions are involved.
R25. Use real public Binance BTCUSDT quotes (`https://data-api.binance.vision/api/v3/ticker/price?symbol=BTCUSDT`) so USDT is not silently equated with USD. R24–R28 supersede R20/R22 Coinbase/USD source and reset semantics for this widget only. Validate the symbol and finite positive price; preserve network errors and stale-state behavior. Only new successful samples may execute virtual orders. Hidden tabs, pause, failed/aborted requests and leaving the page never trade. The 10-second sampling can miss crossings between quotes; execution price is the sampled price, not a guaranteed threshold fill.
R26. Allow minimum/buy and maximum/sell thresholds with numeric input, native arrows and explicit +/− buttons using a configurable positive step (default 10 USDT). Defaults initialize once at first quote: minimum 0.5% below and maximum 0.5% above. Require finite 0 < minimum < maximum. Apply valid edits during a session without resetting balances or triggering an order from the edit itself; evaluate crossings between successive quotes using the current valid thresholds. Invalid drafts cannot start a session or trade and must show a readable message. Starting before any quote may use automatic defaults after the first fresh price.
R27. Start holding USDT with previous price unset. After a downward-crossing buy, hold BTC until a new sampled price crosses strictly above maximum (previous <= maximum, current > maximum), then sell all BTC; while holding USDT buy all-in only on a downward crossing of minimum (previous >= minimum, current < minimum). Remain in this alternating loop without borrowing or adding funds. Equality alone is not a crossing; repeated samples on the same side must not duplicate trades. Dynamic thresholds apply prospectively to the next quote. Fee percent defaults to 0.1% per trade, configurable in [0,5] percent for the next Reset; the active rate is fixed for that run. Model Binance standard fee deduction in the received asset: buy grossBTC = spentUSDT/price, feeBTC = grossBTC*rate, netBTC = grossBTC-feeBTC; sell grossUSDT = soldBTC*price, feeUSDT = grossUSDT*rate, netUSDT = grossUSDT-feeUSDT. Accumulate actual BTC-denominated and USDT-denominated fees separately; headline total commissions is their USDT equivalent converted at each execution price, not at current mark. Never double-charge that equivalent. Show active capital, active fee rate, balances, total equity at latest quote, P/L after charged fees vs starting capital, trade count/state and recent transaction ledger with side, sampled price, spent/received, fee amount/asset and reason.
R28. Label all trades, funds and commissions **simulation**. Explain fee assumptions, no BNB/VIP/pair promotions, no spread/slippage or exchange quantity/lot filters and no persistence; fee estimate is not the user's actual account fee. Link official Binance fee and fee-calculation documentation. Commit updates to master specifications before grounding/source changes. Test initial buy, full sell/rebuy cycle, fee math, no duplicate/equality trades, sample idempotence, invalid settings, live limits, capital/fee edits requiring Reset, cash-only Reset/first-sample reference behavior, stale/pause cleanup and bounded history; run all existing tests/build and deploy only the parallel branch.


## R29 — One durable shared simulation (v2.5.0)
Replace browser-session authority with one server-owned simulation for the parallel `/bitcoin` environment. R29–R32 supersede earlier local/in-memory-per-browser ownership and visibility-controlled engine execution. Persist the entire snapshot in a dedicated PostgreSQL schema/table: settings (capital, fee, minimum, maximum, step), active capital/rate, balances, asset fee totals/equivalent, phase (never started/holding USDT/holding BTC), previous quote, running/paused flag, quote history/summary, trade ledger/count, poll/error metadata and revisions. Opening/reloading/leaving a browser or connecting a second device must only read this state; never initialize, reset, start or pause it automatically. First creation alone seeds default configuration (10000 USDT, 0.1%, step10) and an inactive simulation; no automatic import of inconsistent historical browser-only sessions.
R30. A server scheduler polls Binance about every 10 seconds while shared tracking is running, independently of browser visibility/connections. Start/Reset restores configured USDT with zero BTC/fees/trades/chart and waits for the first reference then a later downward minimum crossing. Pause/resume, manual quote refresh, settings changes and Reset affect everyone and are persisted atomically. Resume keeps balances; neither browser mount nor GET is a simulation command. Initial running market observation may be true even before simulation Start. Preserve the last good quote on provider failure and never fabricate catch-up prices/fills. Display last server sample time and honest interrupted/offline status. Render Free sleep/restarts stop actual execution while asleep: durable state survives and resumes when awake; uninterrupted 24/7 polling is not guaranteed on Free.
R31. PostgreSQL is the sole runtime authority. Serialize all quote processing and commands with a transaction/row lock on the singleton record; persist the entire new snapshot before returning success. Use unique command IDs for replay idempotence and expected control revision for conflicting user commands (quote updates do not invalidate controls). One poll slot per durable next-poll timestamp avoids duplicate quotes/fills across overlapping instances. GET must return no-store snapshots without mutating. API: GET /api/simulation and POST /api/simulation/commands. Validate finite bounded settings, enforce minimum<maximum, keep immutable active capital/fee until Reset, and retain bounded histories (180 quotes,100 trades,128 recent command IDs). Never silently fall back to local simulation or volatile backend state when database configuration fails. Return safe 503 for missing/unavailable storage; retain prior durable state. UI shows connection/loading/conflict errors instead of invented balances and disables commands before first successful load.
R32. Store connection credentials only in Render backend env SIMULATION_DATABASE_URL; never send them to React or commit them. Reuse an existing same-region database only via a dedicated bitcoin_shared schema, preserving other applications/tables. Do not create paid resources or upgrade services. Publish storage SQL, deployment prerequisites and provider/free-plan limitations. All controls are public, explicitly shared demo controls with fictitious funds; warn that actions affect the shared instance. Do not imply identity protection or private account data. Browser views poll/read snapshots and submit explicit commands, with no client trade engine or market polling. Settings editors save valid changes centrally, with dynamic +/- applying centrally; local input drafts are not authoritative state. Validate restart/reload and two-view consistency, quote/command concurrency/idempotence/conflicts, pause persistence, reset/no first buy, provider/storage failure rollback, and existing math/lifecycle regressions. Do not activate the replacement frontend until its backend storage is configured and verified.
